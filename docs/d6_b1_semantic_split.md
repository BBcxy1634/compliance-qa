## 原理

### 语义切分在做什么

固定切分只看字符数。每累计 512 个字符就切一刀，不关心句子和段落是否完整，因此可能把一个政策条件、例外或流程步骤拆到两个 chunk 中。

语义切分先按标题、段落和句子组织内容，再把相邻内容组合到不超过 800 字符的 chunk 中，并保留 64 字符重叠。这样每个 chunk 更容易保持完整语义，边界两侧也有少量上下文。

B1 的 271 个 chunk 少于 B0 的 334 个，主要原因是语义切分减少了生硬断点。

### BGE-M3 检索在做什么

BGE-M3 把每个 chunk 和用户问题分别编码成 1024 维向量。语义相近的内容在向量空间中距离更近。检索时计算问题向量与所有 chunk 向量的余弦相似度，返回最接近的 5 个 chunk。

切分变化影响的是“被编码的对象”，不改变 BGE-M3 的检索算法。因此 B0 和 B1 的差异可以较为直接地归因于 chunk 边界和上下文完整度。

### 为什么检索指标没有提升

B0 的 Hit@5 已经是 1.0，gold unit recall@5 也已达到 0.9767。指标接近上限后，语义切分很难再通过 Top 5 命中率体现优势。

这说明当前语料和问题下，固定切分已经能够把正确页面召回到前 5，切分不是主要瓶颈。这个结果是负向但有效的实验结论，后续报告中应如实保留。

### 为什么答案指标变化

答案正确率从 0.34 变为 0.30，主要不是检索退化，而是抽取式回答对句子选择敏感。语义 chunk 更完整，但候选句更长、更集中，当前拼接逻辑不一定能稳定选出所有关键事实。

多跳题仍然为 0，说明多跳失败不是切分单独能解决的问题，当前抽取式生成缺少跨来源整合能力。

引用覆盖率从 0.94 降到 0.92，表示有更多可答题没有产生非空引用。拒答题误回答从 1 降到 0，但同时可答题误拒答从 3 增加到 4，说明拒答阈值仍需在后续阶段单独优化。

P50 和 P95 各下降约 51 至 53 ms，但当前只运行了一次评测，系统负载也会影响延迟。这里记录的是本次观测值，不将它解释为语义切分的确定性能收益；D11 会用更规范的压测再验证。

## 复现命令

生成语义切分：

```powershell
python -m src.ingest --strategy semantic --output data/processed/chunks.jsonl
```

建立语义向量库：

```powershell
python -m src.embed --chunks data/processed/chunks.jsonl --collection bge_m3_semantic --batch-size 8
```

运行 B1：

```powershell
python evaluate.py --config eval/configs/b1.yaml --chunks data/processed/chunks.jsonl
```

更新 baseline 对比表：

```powershell
python scripts/build_baseline_table.py `
  --run "B0=eval/results/b0/summary.json" `
  --run "B1=eval/results/b1/summary.json"
```
